Executive summary

The project now has a complete inference path: one x86 PE goes through angr CFG recovery, the frozen 187-feature block representation, a function-level GCN and a per-block head, and comes out as a JSON report with function scores and basic-block addresses. The demo binary is a held-out test sample; the CLI selected one anti-debug function and 21 injection functions, and localised 205 injection blocks. The anti-debug function was selected at the function level but no block crossed the conservative 0.94 Stage 2 threshold, so its block list is empty by design.

What is measured. Stage 1 is evaluated on functions, with per-target precision/recall/F1 and average precision. Stage 2 is evaluated on blocks with precision/recall/F1 and IoU, both on oracle positive functions and end-to-end with Stage 1 selection. Test was evaluated once; thresholds were selected on validation only.

Key findings

  • Injection is the strongest target end-to-end. Stage 1 test F1 is 0.4774; Stage 2 end-to-end block F1 is 0.5202 with recall 0.9470. This is consistent with injection's larger positive support and API-call seed structure.
  • Keylogger is the weakest at function level. Test F1 is 0.3376. The label is concentrated: 75.7% of positives come from one cluster and the feature is largely keyboard-state API presence.
  • Anti-debug function detection is moderate, block localisation is conservative. Function F1 is 0.6522 on 27 test functions. The block head reaches precision 1.0000 but recall 0.0588 on oracle functions; the selected threshold is too strict for reliable block recovery.
  • Features are identical between corpus and single-binary inference. A parity test compares all 36,649 block rows for the demo sample and obtains exact equality for features, addresses, function membership, edges, and model probabilities.
  • No malware-family attribution is produced. “Not selected” means no target rule was selected; it is not a benign verdict. The model is trained on malware only.
Metrics in this report are the committed held-out test metrics. The demo sample and its graph are git-ignored; the report contains addresses and scores, not sample bytes.

1. Task and data contract

Stage 1 predicts three independent behaviours for every recovered function. The labels are CAPA namespace matches, not hand-verified ground truth. A function may match more than one target. Class 0 is “no target selected”, not “benign”.

Corpus and labels

  • 2,733 clean samples in the frozen manifest; 2,729 graphs recovered (4 angr failures).
  • 2,749,125 function rows in the three-target split.
  • Positive functions: 448 anti-debug, 1,255 keylogger, 1,349 injection.
  • Split protocol: three-target-cluster-stratified-v3, 70/15/15 by cluster. The old v2 main.json is not used for these targets.
  • Test supports: 27 anti-debug, 153 keylogger, 202 injection functions.

Stage 2 supervision

  • 120,319 masked blocks in 3,044 positive functions.
  • Positive blocks: anti-debug 1,432, keylogger 9,504, injection 15,263.
  • Labels combine CAPA evidence locations with import-resolved API-call seeds. API seeds dominate keylogger and injection positives.
  • Test blocks: 136 anti-debug, 1,344 keylogger, 2,094 injection.

2. Stage 1: function classification

The GCN has two message-passing layers, a residual skip, mean+max pooling, and a small MLP head with three sigmoid outputs. Edges are intraprocedural. Model selection used validation only; the test split was evaluated once.

How to read this table

  • The macro F1 is 0.4890. It is not a family-wide generalisation claim: the test supports are small and clustered.
  • Injection has the largest test support (202) and the highest F1 (0.4774). Keylogger has 153 positives but only 0.3376 F1, reflecting the weak and concentrated label.
  • Anti-debug has only 27 test positives. Its F1 (0.6522) has a wide uncertainty even though precision is relatively high (0.7895).
Label quality caveat. CAPA namespaces are observational labels. 75.7% of keylogger positives and 61.2% of anti-debug positives come from one cluster each; injection is 32.9%. The audit is committed under results/audit/. The labels are reported as-is; they are not renamed or dropped.

3. Stage 2: block localisation

The Stage 2 trunk is the frozen Stage 1 GCN; only a per-block head is trained. “Oracle” uses all true positive functions, so it isolates block-head quality. “End-to-end” uses only functions selected by Stage 1, so it includes Stage 1 false positives and missed functions.

Observations

  • Macro oracle F1 is 0.4586 (IoU 0.3373); macro end-to-end F1 is 0.3723 (IoU 0.2375).
  • Injection dominates: oracle F1 0.7663 and end-to-end F1 0.5202, with end-to-end recall 0.9470.
  • Keylogger oracle F1 is 0.4983; end-to-end F1 is 0.4106. The block labels are API-call-heavy, which the head can recover better than the function-level keylogger pattern.
  • Anti-debug oracle precision is 1.0000 but recall is 0.0588 on 136 test blocks. The 0.94 threshold was selected on 27 validation functions and is too conservative. Its block AP is 0.336, so ranking is better than thresholded recall suggests.
Diagnostic, not ground truth. Stage 2 labels come from CAPA evidence plus API-call seeds. The metrics measure recovery of those seeds, not every malicious block. A localised block is a lead for an analyst, not proof that the block executes a malicious action.

4. Single-binary inference

The implementation adds src/infer/run.py with a CLI, a reusable pipeline, and a JSON report builder. It validates the PE, optionally extracts the CFG with the existing worker, rebuilds the exact features, loads the frozen checkpoints, runs both stages, and writes an atomic JSON report.

./venv/bin/python -m src.infer.run \
  --binary <x86-pe> \
  --out results/infer/<sample>.json

# optional: skip extraction for an existing graph
./venv/bin/python -m src.infer.run \
  --binary <x86-pe> --graph <graph.npz> \
  --out /tmp/opencode/report.json

Feature parity
For the demo sample, single-graph and corpus features are bit-identical: 36,649 rows, 8,633 functions, 1,674 edges, 387 resolved API calls; maximum absolute feature difference 0.0. Stage 1 and Stage 2 probability differences are also 0.0. Two additional held-out samples reproduced the corpus batch selected sets exactly; see results/infer/inference_validation.json.
Architecture and failures
The CLI rejects known x64/ARM machines and PE32+ input before angr. Packed or malformed samples that cannot be recovered return exit code 2 with the worker error. They are never converted into a negative prediction.

Output contract

The JSON schema is cfg-gnn.infer.v1. Each target has present, max_function_score, n_flagged_functions, thresholds, and a function list. Each selected function has func_va, func_rva, score, max_block_score, and blocks sorted by Stage 2 score. The complete field documentation is in docs/inference.md.

5. Limitations and honest interpretation

Labels and scope

  • Weak labels. CAPA matches are not ground truth. The targets are namespace shorthand, not proof of intent.
  • Malware only. There is no benign corpus. Background means “no target rule selected”, not “safe”.
  • Cluster concentration. Keylogger and anti-debug results are dominated by one cluster each. Per-target scores should be read with cluster support, not as broad capability claims.
  • x86 PE only. ELF, ARM, and x64 are out of scope; the 855 x64 BODMAS rows were packed and excluded by the v2 filter.

Pipeline and evaluation

  • Stage 2 is weakly supervised. Its metrics measure recovery of CAPA/API seeds, not complete malicious-block annotation.
  • Anti-debug block threshold is unstable. Only 27 validation functions; oracle F1 0.1111. A higher-recall threshold may be preferable for triage.
  • Static recovery limits. Packed binaries, indirect jumps, and missed code reduce recall. angr failures are reported, not silently dropped.
  • Test reuse. The test split has been evaluated once for each stage. Do not retune on it after design changes.
Open validation. The Ghidra block-label spot-check remains open: 40 functions were selected and 0 verdicts are recorded. The inference CLI does not require Ghidra and does not claim that predicted blocks have been manually validated.
