# Evaluation protocol (pre-registered)

Version: `grouped-kfold-v3`
Registered: 2026-10-22, **before any model run under these labels**.
Owner rule: this protocol does not change after seeing results.

## Why the split changed

The v2 evaluation used a single frozen main split (train/val/test) plus a LOFO
split. The v2 test set is byte-identical in v3 and was deliberately frozen.

The label audit (`results/audit/label_rule_composition.md`) showed the frozen
test set is unusable for `anti_debug_timing`:

| split | label | positives | clusters | top cluster share |
|---|---|---|---|---|
| train | `anti_debug_timing` | 415 | 14 | 66.0% |
| **val** | **`anti_debug_timing`** | **7** | **3** | 57.1% |
| **test** | **`anti_debug_timing`** | **112** | **4** | **89.3%** |

The test split holds 4 clusters, one of which supplies 89.3% of positives, and
`649f6ed9` (aitinject/cryptinject) alone carries 100 of the 112. Validation has
7 positives. Any held-out metric on that split measures one dropper cluster.

The v3 rule is that external samples enter train/val only, which cannot repair a
frozen test distribution. So the **protocol**, not the corpus, had to change.

**The split change is a consequence of the label audit, and it postdates it.**
That ordering is recorded here deliberately: the protocol was revised because
the labels were re-scoped, never because a model scored badly.

## Protocol

### Primary: grouped k-fold over imphash clusters

- `N_FOLDS = 5`, grouped by `cluster_key`. A cluster is never split across folds.
- **Stratified per label**: each fold receives a share of positives for each
  active label, within the constraint that clusters stay intact.
- Near-duplicates cannot cross folds, preserving the original imphash-grouping
  guarantee.
- Assignments are generated by seed, committed as data, and hashed. They are not
  regenerated per training run.

Cluster-level grouping is what makes the confidence intervals meaningful: fold
metrics are aggregated at the cluster level, then bootstrapped over clusters.

### Secondary: leave-one-family-out (LOFO)

- `N_LOFO_REPEATS = 10`, held-out family per repeat, sampled over eligible
  families.
- A family is eligible if it has at least one positive cluster and enough
  positives to compute a metric; eligibility is fixed before training.
- Rationale unchanged from v2: LOFO is the only arm that tests generalization to
  an unseen family rather than an unseen sample of a seen family.

### Reporting requirements (unchanged, still binding)

- Positive-only metrics (precision/recall/AP on positives), never accuracy on a
  class-imbalanced binary task.
- Cluster-level and binary-level bootstrap CIs.
- No-edge and MLP ablations.
- Per-label: positive functions, binaries, families, clusters, largest binary /
  family / cluster share, and held-out positive coverage (binaries and clusters).
- Full-API vs no-API, reported together with the gap. See below.

## The no-API arm (decision 4)

Both active labels are defined by API or instruction features, so an
API-aware model can recover them by memorization rather than by structure. The
no-API arm is therefore a **core experiment**, not a side ablation.

Eligibility for every model comparison: both arms must run under the identical
fold assignment and reporting.

Removal requirements — all three, not just the first:

1. **Import names from call nodes.** Call targets are stripped of symbol
   identity. Dropping API feature columns alone is insufficient: the model still
   reads `VirtualAlloc` off the CFG.
2. **Instruction/immediate patterns that define the rules**, wherever opcode or
   operand features can see them:
   - `rdtsc` / `rdtscp` and `icebp` (defines `execute anti-debugging instructions`);
   - `int3` / software-breakpoint opcodes;
   - the constant `0x40 = PAGE_EXECUTE_READWRITE` (defines `allocate or change
     RWX memory`), in immediates, `lea` offsets, and stack arguments;
   - repeated-call counts to `QueryPerformanceCounter` / `GetTickCount` as a
     *pattern* (e.g. a call repeated within one function), which is itself
     discriminative even without names.
3. **Any feature derived from the above**, including per-function rule-match
   counts, namespace histograms, and string/import tables that name the API.

Reporting: full-API score, no-API score, and the **gap** for every metric.
Interpretation, fixed in advance:

- **The full-API number is not evidence of capability classification.** It is an
  upper bound contaminated by label-defining features.
- **The no-API number is the only honest estimate of structural signal.** If the
  gap is large, the finding is that the model learned the rule, not the
  behaviour.

## Stage 2

**Paused.** Block-level localization is circular under these labels: the
"malicious block" is by construction the block where the rule fired
(`allocate or change RWX memory` has block scope; the anti-debug timing rules do
too). A model would be graded on whether it finds the block the label was
extracted from.

Revisit only if the census yields a label that is not a single
API/instruction pattern. On the current corpus it does not: exactly one rule
passes the census gate and it is one API call.
